# Backend: Vision Project Atlas API

FastAPI over PostgreSQL (asyncpg, plain SQL) with the **Vision Lab** built in:
79 pipelines on YOLO26 and other public models plus proven OpenCV methods,
run in a background thread pool. The models themselves run in
[`models-serve`](../models-serve), which can sit on a GPU server. The API does two things:

- **Catalog and progress.** It serves the 90 projects with search, facets and
  detail. Users can register, track a status and notes per project, and see
  their board.
- **Lab runs.** It accepts images or video (or a built-in sample) for a
  project's pipeline and runs it in the background. It reports progress, then
  saves the results: annotated images and videos, tables, charts, downloads.

## How a run flows

```
POST /api/runs ──> validate slots/params ──> stage files in media/runs/<id>/in
      │                                             │
      └─ inference_run (queued) ──> thread pool ──> pipeline(ctx) ──> media/runs/<id>/out
                                        │                                   │
              status / progress / result written back through the API's event loop
```

Pipelines are synchronous (OpenCV, PyTorch), so they run in worker threads.
The database is async, so a worker never opens its own connection. Every
update it makes is scheduled on the API's event loop
(`app/vision/runner.py`). The engine (`app/vision/`) does not import the
database at all. Uploaded models reach it as file paths registered by the run
router.

Each model step is an HTTP call to models-serve (`MODELS_URL`).
`app/vision/registry.py` is that client. Pipelines keep calling
`ctx.predict(...)` and `manager.use(key)`, and they get back objects that look
like Ultralytics Results. On the first run that uses an uploaded model, the API
pushes the model's file to models-serve. YuNet and SFace are tiny, so their
files are copied here once and they run with OpenCV in the API.

## Running with Docker (recommended)

From the repository root:

```bash
cp backend/.env.example backend/.env    # set JWT_SECRET (see the comment in the file)
docker compose up --build
```

The api container reads `backend/.env`. Compose overrides `DB_HOST` and
`DB_PORT` so it reaches the `postgres` service, and sets `MODELS_URL` to the
`models` container. Uploads, run outputs and uploaded models live in the
`atlas-data` volume (`/data`). Public model weights are files in
`models-serve/models/` on the host. The first run of each lab downloads its
model (5 MB to 200 MB) there. To download them ahead of time:

```bash
docker compose exec models python -m app.download         # core set
docker compose exec models python -m app.download --all   # everything
```

**NVIDIA GPU:** `docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --build`
gives the GPU to the `models` container (it needs the NVIDIA Container Toolkit). To run
the models on another server, see `models-serve/README.md`.

## Running without Docker

You need Python 3.11–3.13 and a PostgreSQL with `database/schema.sql` and
`database/seed.sql` applied. The simplest option is `docker compose up -d postgres`.
You also need models-serve on port 8500: either run it as described in its
README, or use `docker compose up -d models` and publish its port in a
`docker-compose.override.yml`.

```bash
cd backend
python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt -r requirements-ml.txt   # no PyTorch needed here
cp .env.example .env                                     # DB_HOST=localhost, MODELS_URL=http://localhost:8500, set JWT_SECRET
uvicorn app.main:app --reload --port 8000
```

## Auth

Anyone can register. `POST /api/auth/register`, `/login` and `/refresh` return
`{access_token, refresh_token, token_type, user}`.
- Send the access token as `Authorization: Bearer <token>`. It lasts
  `ACCESS_TOKEN_EXPIRE_MINUTES` (30).
- When it expires, the console trades the refresh token
  (`REFRESH_TOKEN_EXPIRE_DAYS`, 7) at `/api/auth/refresh` for a new pair.
  Refresh tokens rotate: each one works once. Presenting a used one again
  revokes all of that account's sessions.
- Every guard in `app/api/deps.py` re-reads the `app_user` row. A deactivated
  account, a role change, a password change or "sign out everywhere" therefore
  applies on the next request. The last three bump `token_version`, which
  every access token carries.
- Roles form one ladder, `user < admin`. Admins edit the catalog, manage
  accounts at `/api/users`, prefetch models, and can share uploaded models
  with everyone.
- The admin guards refuse to delete or demote yourself, and refuse to demote,
  deactivate or delete the last active admin.

## Workspaces

A workspace holds a team's cameras, their events and the models shared with
it. The catalog, lab runs and boards stay per user.
- System admins create workspaces and set each one's camera limit and allowed
  live pipelines (`enabled_pipelines`; `null` allows all).
- Members have a workspace role: `viewer < operator < admin`. Viewers watch;
  operators also run cameras, handle events and share models; admins also
  manage cameras and members. System admins act as admin in every workspace.
- Workspace-scoped routes take the active workspace in the `X-Workspace-Id`
  header (`require_workspace(minimum)` in `app/api/deps.py`).
- Non-members get 404, so workspace ids don't leak. Members of a deactivated
  workspace get 403.
- A workspace admin can't leave the workspace without an admin; a system admin
  can.
- A model uploaded with `workspace_id` is visible to that workspace's members.
  Deleting the workspace hands the model back to its owner.

## Cameras

A camera is a source in a workspace. It can run a **live pipeline**: a lab
pipeline adapted to an endless stream (`app/vision/live/`). It has the same
name and the same settings as its lab pipeline, so the console reuses the
lab's form, and zones and lines are drawn the same way. Where the per-frame
logic can be shared, both use the same code (`ZoneMonitor` in
`pipelines/common.py`). Live pipelines today: `detect` (counts per class),
`track_count` (line in/out) and `restricted_zone` (`zone_entry` events).

**Sources.** `rtsp://`, `rtsps://` or `http(s)://`. For testing:
`sample:<lab sample video>`, or `file:<name>` under `CAMERA_FILES_DIR`
(`camera-files/` in compose). File sources loop at their own frame rate.
Anything else is refused, as are loopback and link-local hosts. Only
workspace admins see the password in a URL.

**Workers.** `app/services/stream_manager.py` is ported from lost-found. Each
running camera has one asyncio task that:
- reads the newest frame
- downscales it to `CAMERA_MAX_SIDE`
- runs the analyzer (model calls go to models-serve; tracking keeps a session there)
- encodes one JPEG that every viewer shares

Blocking work runs on threads. `enabled` is the operator's intent. A
supervisor (every `WORKER_SUPERVISION_INTERVAL_S`) does three things:
- restarts dead or wedged workers with backoff
- starts enabled cameras that have no worker
- stops workers whose camera was disabled or deleted, or whose workspace was
  deactivated

At most `MAX_LIVE_CAMERAS` (8) run at once. Every camera sends `target_fps`
model calls a second, so size this to the model server.

**Live view.** It is a WebSocket at `/api/ws/cameras/{id}?token=`. The token
comes from `POST /api/cameras/{id}/live-token`: it is short-lived and scoped to
one camera, because a browser can't send an Authorization header when it
opens a WebSocket.
- Each frame is a JSON header followed by the JPEG as a binary message.
- `{"type": "status"}` messages say why there's no picture.
- Access is re-checked every minute on an open connection.
- WebSockets were chosen over MJPEG because each MJPEG `<img>` holds one of
  the browser's six HTTP/1.1 connections, which a live wall would exhaust.

## Using your own models

1. Train, for example on your Saudi plates: `yolo detect train data=data.yaml model=yolo26n.pt epochs=100 imgsz=640`.
   The **Auto-label and synthetic dataset builder** lab (project 60) can produce a starting `data.yaml` dataset from your images.
2. Open **Models → Your models** and upload `runs/detect/train/weights/best.pt`. The task and class names are read from the file.
3. In any lab whose task matches (detect, segment, classify, pose, OBB), pick it under **Model**.

Admins can share uploaded models with all users.

## Adding a pipeline

```python
# backend/app/vision/pipelines/my_module.py
from ..core import IMAGE, Param, boxes_of, pipeline
from .common import draw_dets

@pipeline("count_cups", "Cup counter", "Counts cups with YOLO26.", IMAGE,
          [Param("conf", "Confidence", "number", 0.3, 0.05, 0.95, 0.05)], models=["yolo26-detect"], custom_task="detect")
def count_cups(ctx):
    img = ctx.image()
    dets = [d for d in boxes_of(ctx.predict(ctx.model_key("yolo26-detect"), img, conf=ctx.p("conf"))[0]) if d["cls"] == "cup"]
    ctx.add_image(draw_dets(img, dets), "Cups")
    ctx.stat("Cups", len(dets))
```

Import the module in `pipelines/__init__.py`. Then point a project at it with
the project's `lab` field (`database/seed_data.json` plus
`generate_seed.py`, or the admin API). The form, uploads, drawing tools and
results page are generated from the declaration.

## Tests

The API tests run against a real PostgreSQL database. `tests/conftest.py`
creates a fresh `atlas_test` database on the server given by `DB_HOST` /
`DB_PORT`, and loads it from `database/schema.sql` and `seed.sql`. When no
server is reachable, the API tests are skipped and the security unit tests
still run.

Lab runs need models-serve. `tests/test_models_client.py` is the exception: it
tests the client against a fake server.

```bash
# in Docker, against the compose postgres and models
docker compose up -d postgres models
docker compose run --rm --no-deps -v ./backend/tests:/app/tests -v ./database:/sql:ro -e SQL_DIR=/sql \
  api sh -c "pip install -q -r requirements-dev.txt && pytest -q"
```

## Tuning notes

- **One process.** Runs are tracked in this process (the thread pool and the
  prefetch state), so run a single uvicorn worker and scale with `LAB_WORKERS`
  instead. A restart marks unfinished runs as failed.
- **Model server.** If models-serve is down, the catalog, progress and run
  history keep working. Lab runs fail with "Model server unreachable", and
  `/health` reports `models.ok: false`.
- **YOLO26 and YOLOE-26 are AGPL-3.0.** That is fine for learning, research and
  open-source projects. A closed-source commercial product needs an
  [Ultralytics Enterprise license](https://www.ultralytics.com/license).

## Responsible use

- **Faces and biometrics** (verification, attendance roster matching, palmprints, gait): use only with the consent of the people involved, and keep a person in the loop for decisions.
- **Medical labs** are for research and education. They are not a diagnosis.
- **Safety alerts** (falls, PPE, fire, abandoned objects): validate on footage from your own cameras before relying on them.
- **Zero-shot labs** are prototypes. For production accuracy, fine-tune YOLO26 on your own labeled data.
